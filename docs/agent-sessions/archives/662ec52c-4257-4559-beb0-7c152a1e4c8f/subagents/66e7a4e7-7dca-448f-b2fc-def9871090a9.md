## 6. Recommended architecture for persistent overlay

### Best mount point: `F:/Projeto_Kinevo/Kinevo_Alunos/src/app/_layout.tsx`

**Why:**
1. `workout-session` is a **root Stack screen**, sibling to `(main)` tabs — overlays in `(main)/_layout.tsx` **do not render** on the workout screen.
2. **`GlobalWorkoutTicker`** already follows this pattern (root mount, `isWorkoutActive`-driven, survives navigation/background).
3. Matches existing `AppLoadingOverlay` placement (sibling to `NavigationGuard` stack).

**Suggested pattern:**
```tsx
// In RootLayout, alongside GlobalWorkoutTicker:
<GlobalWorkoutTicker />
<WorkoutPersistentOverlay />  // new component
<NavigationGuard />
```

**State source:** `useWorkoutStore` — reuse `isWorkoutActive`, `isWorkoutPaused`, `globalTimerSeconds`, `activeSessionPlayerKind`. Avoid a new UI store unless overlay needs state unrelated to workout (then a minimal `uiStore.ts` for visibility/z-index only).

**Visibility rules to mirror existing logic:**
- Show when `isWorkoutActive && activeSessionPlayerKind !== "circuit"` (or always when active, depending on product)
- Hide on auth/onboarding routes if needed (check `useSegments()`)
- Do **not** mount inside `workout-session.tsx` if overlay must persist when user navigates back to tabs mid-session

**Navigation from overlay:** call same `openWorkoutPlayer` logic or `router.navigate({ pathname: "/workout-session", params: { ... } })` using store's `activeSessionId`, `lastPlanId`/`activePlanId`, and `inProgressExercise.exerciseId`.
