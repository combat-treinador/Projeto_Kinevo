## Architecture Overview

Completed workout history is **not** stored long-term in AsyncStorage. The flow is:

1. **In-session (draft)** → Zustand `workoutStore` → AsyncStorage `@kinevo_active_session`
2. **On finish** → mapped to Firestore payload → `historicoTreinos` collection
3. **Offline** → queued in `@kinevo_offline_workouts`, synced via `syncOfflineWorkouts()`

## 6. Recommendation: Last 3–5 Executions by `exerciseId`

There is **no existing utility** for “last N executions per exercise.” Closest reference: `buildExerciseMaxLoadTimeline()` in `ExerciseProgressionChart.tsx`, which already filters by exercise identity across records.

### Recommended approach

```typescript
import type { WorkoutHistoryRecord, ExercicioConcluidoEntry } from "../services/workout.service";
import {
  resolveExecutedExercises,
  resolveRecordCompletionDateISO,
} from "../services/workoutHistory.adapter";

function resolveEntryIdentity(entry: ExercicioConcluidoEntry): string {
  const id = entry.exerciseId?.trim().toLowerCase();
  return id || (entry.nome ?? "").trim().toLowerCase();
}

export interface ExerciseExecutionSnapshot {
  sessionId: string;
  dateISO: string;
  entry: ExercicioConcluidoEntry;
  /** Normalized CompletedExercise-like view */
  reps: Array<{ setIndex: number; reps: number; weight: number }>;
  pse: number;
}

export function getLastExerciseExecutions(
  records: WorkoutHistoryRecord[], // newest-first (default from fetchWorkoutHistoryPage)
  exerciseId: string,
  limit = 5
): ExerciseExecutionSnapshot[] {
  const target = exerciseId.trim().toLowerCase();
  if (!target) return [];

  const results: ExerciseExecutionSnapshot[] = [];

  for (const record of records) {
    const entry = resolveExecutedExercises(record).find(
      (e) => resolveEntryIdentity(e) === target
    );
    if (!entry) continue;

    const dateISO = resolveRecordCompletionDateISO(record);
    if (!dateISO) continue;

    results.push({
      sessionId: record.id,
      dateISO,
      entry,
      reps: (entry.series ?? []).map((s) => ({
        setIndex: s.setIndex,
        reps: Number(s.reps) || 0,
        weight: Number(s.weight) || 0,
      })),
      pse: Number(entry.pseExercicio) || 0,
    });

    if (results.length >= limit) break;
  }

  return results;
}
```

### Important constraints

1. **No Firestore subcollection query by exercise** — `executedExercises` is embedded; filtering must be client-side.
2. **Paginate if needed** — `useWorkoutHistoryInfinite` loads 15 sessions at a time. If an exercise is done rarely, call `fetchNextPage()` until you have 3–5 hits or `hasNextPage === false`.
3. **Normalize ID consistently** — always `.trim().toLowerCase()` to match `resolveEntryIdentity` / `ExerciseProgressionChart`.
4. **Scope by student** — pass `workoutParams` from `useWorkoutFetchParams()` so trainer impersonation works.
5. **Prefer `exerciseId` over name** — name fallback handles legacy docs but can collide if names repeat across plans.
6. **Place the utility** in `workoutHistory.adapter.ts` (alongside `buildHistorySessionRows`) or a small `exerciseHistory.utils.ts` — reuse `resolveExecutedExercises` and `resolveRecordCompletionDateISO`.

### Usage in a component

```typescript
const { records, fetchNextPage, hasNextPage } = useWorkoutHistoryInfinite();
const targetId = resolveExerciseId(activeExercise);

const lastExecutions = useMemo(
  () => getLastExerciseExecutions(records, targetId, 5),
  [records, targetId]
);

// Optionally extend with useEffect to auto-fetch pages until lastExecutions.length >= 5
```

This aligns with existing conventions and avoids touching the Zustand layer (which only holds the current session draft).
